# Аутентификация и защищённый канал VRack2

Документ описывает, как клиент **узнаётся** мастером VRack2 (по WebSocket) и как дальше
**безопасно** передаются запросы и ответы. Протокол построен на двух стандартизованных
шифрах — **ECDH P-256** (асимметричный обмен ключами) и **AES-256-GCM** (шифрование с
проверкой подлинности) — плюс **HKDF-SHA256** для вывода ключа канала. В референс-реализации
(сервер `Guard` и клиент) используются только встроенные модули Node.js (`crypto`).

> Готовый рабочий клиент — [`vrack2-client.mjs`](./vrack2-client.mjs). Он авторизуется в
> обоих режимах и получает список сервисов.

## Термины

| Термин | Что это | Важно |
|---|---|---|
| **KID** | Публичный идентификатор ключа (поле `key` в записи). Например `default`. | **Передаётся открыто.** По нему сервер выбирает запись. |
| **Ключ (запись)** | `{ name, level, key, private, public }`. | Тип определяется полями `private` / `public`. |
| **serverPub** | Публичный ключ **клиента** (P-256), который сервер использует для ECDH. | Хранится на сервере. Его утечка **не раскрывает** канал. |
| **Приватный ключ клиента** | Приватная часть P-256 пары (PEM), которой владеет только клиент. | **Никогда не отправляется** на сервер. |
| **verify (session)** | Случайный вызов (challenge) на 16 байт, выданный сервером при `apiKeyAuth`. | Клиент шифрует его в первом кадре — это доказательство владения ключом. |
| **ek (ключ канала)** | 32-байтовый симметричный ключ, выводимый обеими сторонами одинаково. | Никогда не передаётся по сети. |
| **Кадр (frame)** | Единичное зашифрованное сообщение — «конверт» вокруг обычного JSON. | `base64url(nonce ‖ ciphertext ‖ tag)`. |
| **AAD** | Данные, «приклеенные» к кадру: `clientId`, `seq`, направление, `verify`. | Не передаётся, но участвует в проверке подлинности. |
| **seq** | Счётчик сообщений в каждом направлении (1, 2, 3, …). | Защита от повтора (replay). |

## Типы ключей

Тип определяется **наличием** полей `private` и `public`:

| Тип | Поля | Аутентификация | Трафик |
|---|---|---|---|
| **Обычный** (plain) | `private` и `public` пусты | `apiKeyAuth` → сразу `cipher:false` | Обычный JSON, без шифрования |
| **Асимметричный** (ECDH) | `public` заполнен | `apiKeyAuth` → `apiPrivateAuth` (proof) | Кадр GCM (v2) |
| **Устаревший** (shared secret) | `private` заполнен, `public` пуст | `apiKeyAuth` → `apiPrivateAuth` (proof) | Кадр GCM (v2) |

- **Асимметричный** — современный безопасный режим. На сервере хранится только **публичный**
  ключ клиента, приватный живёт у клиента. Угон публичного ключа **ничего не раскрывает**.
- **Устаревший** — общий секрет (оба знают одно значение). Оставлен для совместимости с
  ранее созданными ключами. Новый ключ создавать в этом режиме **не рекомендуется**.
- **Обычный** — для локального/офисного доступа. Стандартный ключ `default` — именно он.

## Модель безопасности

| Угроза | Как защищаем |
|---|---|
| Прослушка трафика (чтение данных) | AES-256-GCM. |
| Подмена / вставка бита / инъекция сообщения | Метка подлинности GCM (tag) + AAD. |
| Повтор (replay) записанного кадра | Счётчик `seq` в AAD: чужой/старый счётчик не даст tag сойтись. |
| Перенос кадра на другое соединение/клиента | `clientId` + направление в AAD. |
| Перенос кадра в другую сессию (даже при том же `clientId`) | `verify` (session) в AAD: чужая сессия не сойдётся. |
| Кража публичного ключа (асимметричный) | **Ничего не раскрывает** — канал не определяется без приватного ключа клиента. |

**Что протокол НЕ даёт:** он не удостоверяет **сервер**. Злоумышленник, ставший между
клиентом и сервером (MITM), может подменить сервер — клиент не отличит его от настоящего,
потому что сервер не предъявляет собственного ключа. Если это критично (а в продакшене
обычно критично), поверх WebSocket включают **TLS (WSS)** — сертификат подтверждает
подлинность сервера. Протокол и TLS не противоречат друг другу: v2 защищает канал от
прослушки на недоверенной сети, TLS дополнительно подтверждает, что вы общаетесь с вашим
сервером.

## Ключевой материал и вывод ключа канала

### Асимметричный режим (ECDH)

Клиент имеет пару ключей P-256: **приватный** (PEM, у клиента) и **публичный**. При создании
ключа (`apiKeyAdd` с `cipher:true`) сервер **генерирует** эту пару и: публичный сохраняет у
себя (поле `public`), приватный **возвращает клиенту один раз** (в ответе, как PEM). Дальше
приватный ключ не передаётся по сети никогда.

Обе стороны выводят одинаковый ключ канала `ek` из ECDH-общего секрета:

```
shared = ECDH(clientPriv, serverPub)        // 32 байта, P-256
ek     = HKDF-SHA256( ikm = shared,
                      salt = (пусто),
                      info = "vrack2/v2/ek",
                      len  = 32 )
```

Секрета «напрямую» нет: общий секрет появляется только как результат ECDH, и его не знает
ни одна из сторон по отдельности, пока не выполнен обмен.

### Устаревший режим (shared secret)

Для ключей, созданных до перехода на асимметрию (поле `private` — общий секрет):

```
ek = HKDF-SHA256( ikm = private (байты),
                  salt = "vrack2/v2",
                  info = "vrack2/v2/ek",
                  len  = 32 )
```

Секрет **не используется** как ключ шифра напрямую; из него выводится `ek`. Обе стороны
считают одинаково. (В отличие от ECDH, здесь соль — `"vrack2/v2"`, а не пустая.)

## Кадр — формат зашифрованного сообщения

Каждое зашифрованное сообщение (proof и все запросы/ответы) — это **кадр**:

```
frame = base64url( nonce ‖ ciphertext ‖ tag )
```

| Часть | Длина | Что это |
|---|---|---|
| `nonce` | 12 байт | Случайные 96 бит, уникальные для кадра (генерируются отправителем). |
| `ciphertext` | N байт | Результат AES-256-GCM над полезной нагрузкой. |
| `tag` | 16 байт | Метка подлинности GCM. |

Полезная нагрузка (payload) — **обычный JSON-сообщение** VRack2 (`command` / `data` /
`_pkgIndex` / `result` / `resultData`). Протокол — транспортный/шифрующий слой; команды
для приложений выглядят так же, как и раньше.

## AAD — привязка кадра к сессии

**AAD (Additional Authenticated Data)** — данные, которые **не шифруются**, но участвуют в
вычислении метки подлинности. Если хотя бы один байт AAD на стороне получателя не совпадёт —
проверка tag не пройдёт. AAD не передаётся: обе стороны вычисляют его по правилу.

```
AAD = {"c":<clientId>,"s":<seq>,"d":"<req|res>","v":<verify>}
```

| Поле | Значение | Зачем |
|---|---|---|
| `c` | `clientId`, выданный сервером соединению | Не даёт перенести кадр на другое соединение. |
| `s` | `seq` — счётчик исходящих сообщений стороны-отправителя (1, 2, 3, …) | Не даёт повторить (replay) записанный кадр. |
| `d` | `req` (клиент→сервер) или `res` (сервер→клиент) | Не даёт подменить направление. |
| `v` | `verify` — вызов сервера из `apiKeyAuth` | Не даёт перенести кадр в другую сессию. |

**Правила `seq`:** счётчик **исходящих** сообщений стороны-отправителя, начиная с 1.
Получатель знает, сколько сообщений получил от пира, и ожидает ровно следующее. Для
асимметричного режима:

- **proof** — первый исходящий клиента → `seq = 1` (`req`).
- **первая команда** после auth → `seq = 2` (`req`).
- **первый ответ** сервера → `seq = 1` (`res`).

## Установление канала (handshake)

### Шаг 0. Соединение

Клиент открывает WebSocket `ws://<host>:4044` (по умолчанию порт 4044). Сервер присваивает
соединению `clientId`. На этом шаге ещё ничего не шифруется.

### Шаг 1. Идентификация (`apiKeyAuth`)

Клиент сообщает **KID** (открыто). Сервер находит запись:

- обычный ключ → сразу авторизован, `cipher:false`;
- ключ с шифрованием → выдаёт вызов `verify` (и, для ECDH, публичный ключ `serverPub`).

```
Клиент -> Сервер:
{ "command": "apiKeyAuth", "data": { "key": "default" } }

Сервер -> Клиент   (асимметричный ключ):
{
  "command": "apiKeyAuth",
  "result": "success",
  "clientId": 12,
  "resultData": {
    "verify": "c3J2LW5vbmNlLWZvci1leGFtcGxlLXNjcmlwdA",
    "serverPub": "-----BEGIN PUBLIC KEY-----\nMFkw...\n-----END PUBLIC KEY-----",
    "cipher": true
  }
}
```

`verify` — **вызов**: сервер просит клиента доказать владение ключом, не раскрывая его.

### Шаг 2. Доказательство владения (`apiPrivateAuth`)

Клиент **шифрует полученный `verify`** в первом кадре (AES-256-GCM, AAD `{c, s:1, d:"req",
v:verify}`). Только тот, кто знает приватный ключ (и, значит, выводит тот же `ek`), соберёт
кадр, который сервер расшифрует. Сервер проверяет tag и что расшифрованный текст совпал с
его `verify`.

```
Клиент -> Сервер:
{ "command": "apiPrivateAuth", "data": { "frame": "<base64url-кадр>" } }

Сервер -> Клиент:
{
  "command": "apiPrivateAuth",
  "result": "success",
  "clientId": 12,
  "resultData": { "level": 1000, "cipher": true }
}
```

После успешного `apiPrivateAuth` **канал установлен**: все последующие сообщения идут кадрами.

## Канал данных

После handshake каждый запрос — кадр, каждый ответ — кадр. **В отличие от handshake, сами
сообщения кадра передаются «как есть» — строка кадра является текстом WebSocket-сообщения**
(не обёртка `{ command, data: { frame } }`). Внутренности кадра — обычное JSON-сообщение.

```
Запрос  (клиент -> сервер):  <base64url-кадр>
   payload: { "command": "serviceList", "_pkgIndex": 2, "data": {} }
   AAD:     { "c": 12, "s": 2, "d": "req", "v": "<verify>" }

Ответ   (сервер -> клиент):  <base64url-кадр>
   payload: { "command": "serviceList", "_pkgIndex": 2, "result": "success",
              "resultData": { "master": { "id": "master", "run": true } } }
   AAD:     { "c": 12, "s": 1, "d": "res", "v": "<verify>" }
```

Корреляция запроса и ответа — по `_pkgIndex` **внутри** payload (как и в обычном режиме).

## Обработка ошибок

| Ситуация | Реакция |
|---|---|
| Неверный KID (нет записи) | Сервер отклоняет `apiKeyAuth` (`AKEYM_KEY_NOT_FOUND`). |
| Неверный proof (tag не сошёлся / payload ≠ verify) | Сервер отклоняет `apiPrivateAuth`; канал НЕ устанавливается. |
| Кадр с не-ожидаемым `seq` (повтор) | Не совпадёт AAD → tag не сойдётся → отклоняем. |
| Повреждённый/подменённый кадр | `frameDecrypt` бросает «unable to authenticate data» → отклоняем. |
| Любой сбой целостности | Соединение считать испорченным: закрыть и пройти handshake заново. |

Не логируйте `verify`, `ek`, кадры, приватный ключ — только KID, `level`, `clientId` и код
ошибки.

## Рекомендации по использованию

1. **Удаляйте стандартный `default`** (обычный ключ, доступ без шифрования) и выдавайте
   асимметричные ключи с нужным `level`.
2. **Приватный ключ клиента** храните локально (файл, secrets-менеджер, HSM). Он
   возвращается один раз при создании — не сохраняйте его в логи и не отправляйте повторно.
3. **Публичный ключ** (`public` в записи) можно свободно передавать/бэкапить: его утечка
   не раскрывает канал.
4. **Ротация ключей** — создайте новый ключ (`apiKeyAdd`), переведите на него клиентов и
   удалите старый (`apiKeyDelete`). Старый ключ перестаёт работать немедленно.
5. **TLS (WSS)** — включите поверх WebSocket, чтобы подтвердить подлинность сервера
   (протокол сам сервер не удостоверяет).
 6. **`level`** — минимально необходимый доступ: 0 — только чтение, 1000 — полный
    (включая управление ключами). Выдавайте меньше, если достаточно.
 7. **`apiKeyList`** возвращает только метаданные — `id`, `name`, `key`, `level`.
    Ключевой материал (`private`, `public`) и `description` наружу **не отдаются**:
    читатель (level 1) не может узнать секреты других ключей. Приватный ключ выдаётся
    один раз, в ответе `apiKeyAdd`.
